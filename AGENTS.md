# Repository Guidelines

## Project Structure & Module Organization

Implementation is in `R/`; tests and shared fixtures are in `tests/testthat/`.
Put long-form examples in `vignettes/`, data-building scripts in `data-raw/`,
packaged data in `data/`, and supporting material in `inst/`. Treat `man/`,
`NAMESPACE`, and `docs/` as generated outputs.

## Architecture & Extension Guidance

Read `vignettes/code_structure.Rmd` before architectural changes. It maps the
gonad component, release functions, seasonal reproduction and encounter
dispatch, plots, and fixtures. Use `other_params()` accessors; avoid direct
slot writes unless required by the mizer API.

For extension registration, dispatch, versioning, or persistence changes,
follow `.claude/skills/create-extension-package/SKILL.md` and verify installed
mizer documentation. Treat the vignette as a current-code map and the skill as
the maintenance workflow. Check its rules for `recordExtension()`, coercion,
marker classes, `NextMethod()`, and composable `project*` methods rather than
copying existing patterns.

## Build, Test, and Development Commands

- `R -q -e 'devtools::load_all()'` loads package code for interactive work.
- `R -q -e 'devtools::test()'` runs the complete testthat suite.
- `R -q -e 'devtools::document()'` regenerates roxygen output.
- `R -q -e 'devtools::check()'` performs the package-level pre-commit check.
- `R -q -e 'pkgdown::build_site()'` rebuilds `docs/` after documentation work.

## Coding Style & Naming Conventions

Use four-space indentation (`.lintr`) and `<-` for assignment. Follow nearby
code: `snake_case` for locals and established names such as
`setSeasonalReproduction()` for public APIs. Document exports with roxygen2;
never hand-edit `.Rd` files or `NAMESPACE`. Run `lintr::lint_package()` after
broad refactors.

## Testing Guidelines

Use testthat edition 3. Name files `test-<feature>.R`; write focused
`test_that()` cases for observable behaviour. Add regression coverage for bug
fixes and test both object classes and numerical results. Keep simulations
short and progress bars disabled. No coverage threshold is specified, but all
changed behaviour should be tested.

## Commit & Pull Request Guidelines

Keep commits focused and use short, imperative subjects. Pull requests should
explain motivation and model impact, link issues, list checks run, and note
documentation changes. Include before/after plots when graphical or simulated
output changes.

## Agent-Specific Instructions

Before changing mizer code, read `MIZER-AGENTS.md` and its matching task skill;
consult installed documentation for every function signature. Keep
project-specific notes outside the managed block above.
